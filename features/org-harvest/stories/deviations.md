# Deviations from Plan: org-harvest

**Last Updated:** 2026-08-28

Track any changes from the per-story implementation plan. Each deviation is logged with reasoning.

### DEV-1: Extended Story 1's `StaticTokenCredentialProvider` with an optional known expiry
**Story:** Story 3
**Planned:** Implement AC-7.4 ("does not begin a wait that would outlast the remaining credential lifetime when it cannot refresh") purely in `transport.py`, reading `credentials.seconds_until_expiry()` as Story 1 already defined it.
**Actual:** `StaticTokenCredentialProvider` (Story 1) gained an optional `expires_at` constructor parameter. Without it, `seconds_until_expiry()` still returns `None` exactly as Story 1 built it — behavior for every existing caller and test is unchanged.
**Reasoning:** `can_refresh()` is `False` only for `StaticTokenCredentialProvider`; `AppKeyCredentialProvider` always refreshes itself, so it never needs this protection. But `StaticTokenCredentialProvider.seconds_until_expiry()` always returned `None` (unknown), which means the AC-7.4 safety check in `transport.py` — which only fires when `remaining_credential is not None` — could *never* trigger for the one credential type the AC exists to protect. The check as originally planned would have been structurally present but functionally inert. Since a pre-minted token's expiry is known to whoever minted it (GitHub's mint response includes `expires_at`), exposing it as an optional parameter lets a caller who has it opt into real protection, while a caller who doesn't gets the exact prior behavior (reactive detection on a 401, per AC-3.4).
**Impact:** None on Story 1's existing tests or behavior (new parameter defaults to `None`). Story 15 (library API) should mention this option when documenting programmatic use of a pre-minted token. No CLI flag was added for it in Story 1 — deliberately out of scope for this fix, since the spec's AC-3.8 doesn't call for one; a CLI flag can be added later without breaking this design if it turns out to be wanted.

### DEV-2: Extended `CredentialProvider` protocol with `permissions`/`repository_selection`
**Story:** Story 4
**Planned:** Preflight (AC-6.1) determines "which permissions the active token carries and whether the installation is scoped to selected repositories" against whichever `CredentialProvider` it's given.
**Actual:** Promoted `permissions: dict[str, str] | None` and `repository_selection: str | None` from `AppKeyCredentialProvider`-only attributes (Story 1) to `CredentialProvider` Protocol members, with `StaticTokenCredentialProvider` now setting both to `None`.
**Reasoning:** Preflight needs to read these fields generically across both credential forms without `isinstance` branching or `hasattr`/`type: ignore` workarounds. GitHub genuinely has no endpoint to introspect a pre-minted token's granted permissions, so `None` for the static-token case isn't a gap in this story's implementation — it's a real API limitation, which preflight surfaces honestly ("permissions unknown for a pre-minted token") rather than pretending to verify what it can't.
**Impact:** None on Story 1's tests (both new fields already existed on `AppKeyCredentialProvider` from Story 1; only `StaticTokenCredentialProvider` and the Protocol declaration changed, and `StaticTokenCredentialProvider`'s existing tests don't inspect these fields).

### DEV-3: Extracted preflight's rate-limit extractor into a shared `graphql.py` module
**Story:** Story 5
**Planned:** Story 5's org-level fetch engine needs the exact same `rateLimit { limit remaining resetAt }` extraction preflight (Story 4) already implemented as a private `_extract_graphql_budget` function.
**Actual:** Moved that function, unchanged in behavior, to a new `src/org_harvest/graphql.py` as public `extract_rate_limit_snapshot`, and updated `preflight.py` to import and use it instead of its own copy.
**Reasoning:** A second hand-rolled copy of the same JSON-shape extraction is exactly the kind of drift the declarative-registry decision (architecture.md, Decision 1) exists to avoid elsewhere — the same principle applies here even though this isn't dataset-registry code. One shared, tested helper is safer than two copies that could silently diverge (e.g. if GitHub's rate-limit shape ever changes).
**Impact:** None on Story 4's existing tests or behavior — `preflight.py`'s public API and every test in `tests/test_preflight.py` are unaffected; only the internal extraction helper moved. A new `tests/test_graphql.py` covers the extractor directly.

### DEV-4: Extracted `_snake_case`/`_flatten_node` out of Story 5's `org_level.py` into a shared `harvest/flatten.py`
**Story:** Story 6
**Planned:** Story 6's repository-level fetch engine needs the exact same GraphQL-node-to-record flattening logic (camelCase-to-snake_case key rename, identity synthesis for node types with no `id`) that Story 5 wrote as private helpers in `org_level.py`.
**Actual:** Moved `_snake_case`/`_flatten_node`, unchanged in behavior, to `src/org_harvest/harvest/flatten.py` as public `snake_case`/`flatten_node`, and updated `org_level.py` to import and use them.
**Reasoning:** Same rationale as DEV-3 — a second hand-copy of identical flattening logic in `repo_level.py` would be exactly the kind of drift the declarative-registry decision exists to prevent elsewhere in this codebase. One shared, already-tested (via Story 5's existing tests, which continue to pass unchanged) implementation is safer than two copies.
**Impact:** None on Story 5's behavior or tests — `org_level.py`'s public API is unchanged; only the internal helper functions moved and were renamed from private (`_snake_case`, `_flatten_node`) to public (`snake_case`, `flatten_node`) since they now have two callers across module boundaries.

### DEV-5: Consolidated `DatasetOutcome` into `gaps.py` as a single shared type
**Story:** Story 6
**Planned:** Story 6's `RepoLevelResult` needs a per-dataset outcome shape (name, record count, gaps) — the exact same shape Story 5's `OrgLevelResult` already defined as `org_level.DatasetOutcome`.
**Actual:** Rather than `repo_level.py` defining its own structurally-identical `DatasetOutcome`, the type was moved (unchanged) into `gaps.py` — the module already owning the closely related `Gap` type — and both `org_level.py` and `repo_level.py` now import it from there. The package root re-export (`org_harvest.DatasetOutcome`) now points at `gaps.DatasetOutcome` instead of `org_level.DatasetOutcome`; the public name and shape are unaffected.
**Reasoning:** Two independently-defined dataclasses with identical fields are a drift risk the moment one of them changes — a caller that aggregates outcomes from both phases (Story 10's `run` command will do exactly this) should not have to know or care which phase produced which outcome.
**Impact:** None on Story 5's tests (they never imported `DatasetOutcome` by name) or public API (the re-exported name and shape at `org_harvest.DatasetOutcome` are identical).

### DEV-6: `_OrgLevelHarvester` and `_RepoLevelHarvester` now require a `systemic_guard`
**Story:** Story 7
**Planned:** Story 7 adds systemic-failure detection as a new, additive capability layered on top of Stories 5/6's existing fetch engines.
**Actual:** Rather than making `systemic_guard` optional on the private `_OrgLevelHarvester`/`_RepoLevelHarvester` constructors (Story 5/6 internals, not public API), it is a required keyword argument — the public `fetch_organization_directory()`/`fetch_repository_datasets()` functions default it to a fresh `SystemicFailureGuard()` when the caller passes none, so the *public* API gained an optional parameter, not a required one.
**Reasoning:** Making the internal constructor's parameter optional-with-a-default would mean two different places decide what "no guard supplied" means (the harvester class and the public function); requiring it on the internal class and defaulting it exactly once, in the public entry point, keeps that decision in one place.
**Impact:** Every existing test in `tests/test_org_level.py` and `tests/test_repo_level.py` that constructs `_OrgLevelHarvester`/`_RepoLevelHarvester` directly (rather than going through the public `fetch_*` functions) was updated to pass `systemic_guard=SystemicFailureGuard()`. No public API or behavior changed — a caller of `fetch_organization_directory`/`fetch_repository_datasets` without the new `systemic_guard=` argument sees identical behavior to before this story, now protected by the default guard's thresholds.

### DEV-7: Declared `repositories` as an implicit dependency of every repository-level dataset
**Story:** Story 11
**Planned:** AC-2.6 ("selecting a dataset that depends on another automatically includes the dependency") is implemented generically in a new `selection.py`, walking each `DatasetSpec.depends_on` declared by Story 4's catalog.
**Actual:** Story 4's `catalog.py` did not declare `depends_on=("repositories",)` on any of the 15 default-tier or 8 optional-tier repository-level `DatasetSpec` entries — only `team_members`/`team_repositories` had `depends_on` set. Without it, a selection like `--datasets issues` would resolve to just `("issues",)`, and Phase 2 would have no `repositories.ndjson` to read (architecture.md, Decision 4: Phase 2 fans out over exactly what Phase 1 wrote there) — silently producing zero records rather than fetching anything. Added `depends_on=("repositories",)` to all 23 repository-level `DatasetSpec` entries in `catalog.py`.
**Reasoning:** This is a real, pre-existing structural dependency (Phase 2 cannot run without Phase 1's repository list), not a new relationship Story 11 invents — Story 11's dependency-closure mechanism only surfaces a gap that already existed in the registry's data. Encoding it as `depends_on` (rather than, say, special-casing "any repo-level dataset needs repositories" in `selection.py`) keeps the registry the single source of truth for dependency information, consistent with architecture.md Decision 1.
**Impact:** None on Story 4's existing tests (`test_registry.py` doesn't assert an empty `depends_on` for any repo-level dataset) or on Stories 5-10's behavior — `fetch_organization_directory`/`fetch_repository_datasets` don't read `depends_on` themselves; only `resolve_dataset_selection()` (this story) does. A caller who selects a repo-level dataset without also selecting `repositories` now gets `repositories` auto-included and reported (AC-2.6), where previously (pre-Story-11, when no dataset narrowing existed at all) every dataset always ran unconditionally so the gap was unreachable.

### DEV-8: Fixed a latent cross-dataset cursor bug in `repo_level.py`'s `_RepoState` reuse
**Story:** Story 11
**Planned:** AC-2.9 (per-repository-level-collection item cap) stops a repository's pagination early once its cap is reached, leaving `hasNextPage: true` unresolved for that dataset.
**Actual:** While implementing the cap, found that `_RepoState` objects are constructed once per `fetch_repository_datasets()` call and reused, unreset, across every dataset's `fetch_repo_dataset(spec, list(repos))` call in its loop over `_REPO_CONNECTIONS`. A repository whose pagination for one dataset ended with `hasNextPage: false` retains its cursor from the second-to-last page it fetched (the code only writes `repo.cursor` when `hasNextPage` is `true`) — that stale, non-`None` cursor then seeded the *next* dataset's first-page query for the same repository, silently skipping that dataset's earlier records. This is a pre-existing Story 6 defect (reachable by any repository needing 2+ pages for one dataset, followed by any other dataset), not something Story 11's cap introduced — but the cap made it actively load-bearing (a capped repository is guaranteed to have a real, unresolved cursor to leak), so it had to be fixed for the cap to behave correctly at all. Fixed by resetting `repo.cursor = None` for every repository at the start of each `fetch_repo_dataset()` call.
**Reasoning:** Leaving a known-reachable data-loss bug in place while building a new feature that would make it fire on every capped run was not acceptable; the fix is minimal (three lines), touches only `_RepoState` objects owned entirely by this module, and is covered by a dedicated regression test (`TestCursorIsolationAcrossDatasets`) proving the specific failure mode.
**Impact:** Every existing `tests/test_repo_level.py` test still passes unchanged (all used single-page fixtures, where this bug was unreachable — `repo.cursor` was already `None` for every dataset since it's never mutated on a `hasNextPage: false` page). No public API changed.

### DEV-9: Superseded DEV-8's blanket cursor reset with a checkpoint-driven per-dataset reset
**Story:** Story 12
**Planned:** Story 12 needs `repo_level.py`'s per-repository cursor tracking to survive a resume — a repository's stored cursor (or `CURSOR_DONE`) must seed `fetch_repo_dataset()`'s queue instead of starting blind.
**Actual:** DEV-8's fix (blanket `repo.cursor = None` for every repository at the start of each `fetch_repo_dataset()` call) is incompatible with resume: it would erase a real stored cursor exactly like it erases a stale leaked one, since both are just "a non-`None` value" to that code. Replaced it with a lookup against `self._checkpoint.state.cursors[f"{spec.dataset}:{repo.id}"]` at the start of `fetch_repo_dataset()` — repositories already marked `CURSOR_DONE` for this dataset are skipped from the queue entirely (not re-fetched at all), and every other repository's `cursor` is set to exactly its stored value (a real cursor, or `None` if never attempted for this dataset) before being enqueued. This fixes the same cross-dataset leak DEV-8 fixed (a stale cursor from a *different* dataset is never in `cursors[f"{spec.dataset}:..."]`, keyed as it is by this exact dataset) while also being the mechanism that makes resume itself possible.
**Reasoning:** One checkpoint-driven reset serves both purposes (correctness for the non-resumed case, and real resume capability) more correctly than DEV-8's blanket reset ever did — DEV-8's fix could only ever distinguish "leaked from another dataset" from "legitimately in progress for this one" by accident (both looked like "some cursor value"); reading the per-dataset checkpoint key removes the ambiguity entirely.
**Impact:** None on any existing test's assertions — `TestCursorIsolationAcrossDatasets` (DEV-8's regression test) still passes unchanged, since a checkpoint with no stored cursor for a given `{dataset}:{repo.id}` key returns `None` from `.get()`, identical to DEV-8's blanket reset for that case. New coverage: `TestResume` in `test_repo_level.py`.

### DEV-10: AC-4.6's tolerant trailing-line read changed two Story 8 test fixtures' meaning
**Story:** Story 12
**Planned:** AC-4.6 requires that an abruptly-killed run's truncated trailing NDJSON line be silently discarded on the next read, rather than treated as a conversion failure.
**Actual:** `read_ndjson_tolerant()` (in `output.py`, now used by `finalize.py` in place of the old strict `_read_ndjson`) discards exactly one unparseable line only when it is the *last* line in the file, and still raises `json.JSONDecodeError` for a malformed line anywhere else. Two pre-existing Story 8 tests — `test_conversion_failure_is_a_gap_and_leaves_ndjson_untouched_ac_8_4` and `test_a_conversion_failure_in_one_dataset_does_not_block_others` — happened to put their single malformed line as the *trailing* line in their fixture, so under the new tolerant reader that line was silently discarded (counted as "0 gaps, N-1 good records") instead of raising a conversion-failure gap as those tests originally asserted. Fixed by rewriting both fixtures so the malformed line is *not* trailing (a valid record line follows it) — preserving each test's original intent (a genuinely malformed line still fails conversion) while remaining compatible with AC-4.6's new trailing-line tolerance. A new test, `test_a_truncated_trailing_line_is_discarded_not_a_conversion_failure_ac_4_6`, covers the specific trailing-truncation case those two tests used to (incidentally) exercise.
**Reasoning:** This is a genuine, deliberate tension between two ACs from different stories — AC-8.4 ("malformed data still fails conversion, recorded as a gap") and AC-4.6 ("a killed process's truncated trailing line is expected and forgiven, not corruption") — not a bug in either story. The two failure signatures are genuinely different (a truncated trailing line is exactly what an abrupt kill mid-write produces; a malformed line anywhere else is not explainable that way), so a reader that treats them differently is the correct resolution, not a regression.
**Impact:** Both fixed tests still assert their original intended behavior (malformed data → conversion failure gap, file untouched); only their fixture content changed, not their assertions. No production code outside `output.py`/`finalize.py` (already covered in this story's main changes) was touched for this.

### DEV-11: Non-paginated repo-level connection specs previously received no cursor/completion tracking at all
**Story:** Story 12
**Planned:** Story 12's resume mechanism marks each repository `CURSOR_DONE` once a dataset's fetch for it is fully attempted, so a resumed run knows what to skip.
**Actual:** While wiring this into `_run_batch()`, found that `_RepoConnectionSpec` entries with `paginated=False` (e.g. `repo_custom_property_values`, `languages`) previously took a code path that never called `self._checkpoint.set_cursor(...)` at all — paginated specs got a cursor or nothing depending on `hasNextPage`, but non-paginated specs got neither a cursor nor a `CURSOR_DONE` marker, ever. This was harmless before Story 12 (nothing read cursors back), but would have made a resumed run re-fetch and duplicate every non-paginated dataset's records for every repository, since there would be no record that they were ever attempted. Fixed by adding an `else: self._checkpoint.set_cursor(f"{spec.dataset}:{repo.id}", CURSOR_DONE)` branch for the non-paginated case in `_run_batch()`, run immediately after a successful (non-`None`) fetch.
**Reasoning:** This is a genuine gap Story 12 needed to close for AC-4.5 ("resumed runs do not duplicate records") to hold for all 8 non-paginated repo-level datasets, not just the 15 paginated ones — found and fixed proactively during design, before any test exercised it, rather than discovered later as a resume-time data-duplication bug.
**Impact:** None on any existing test (no prior test asserted the *absence* of a checkpoint entry for a non-paginated dataset). New coverage: `test_a_done_non_paginated_spec_is_skipped_on_resume` in `test_repo_level.py`'s `TestResume`.

### DEV-12: `run_snapshot()` never actually persisted `repository_filter` to a fresh checkpoint before this story
**Story:** Story 13
**Planned:** AC-4.8 needs a resumed run's recorded repository filter compared against the current request's, to refuse a resume whose filter doesn't match.
**Actual:** Tracing `CheckpointStore.create()`'s call site in `run.py` (unchanged since Story 10) showed it never passed `repository_filter=` at all — every checkpoint's `repository_filter` field was `None` regardless of what `--repos`/`--exclude-archived`/`--exclude-forks` the run actually used, and the two new `repository_exclude_archived`/`repository_exclude_forks` fields this story adds to `CheckpointState` had nothing to be populated from either. Fixed by having `run_snapshot()`'s fresh-checkpoint branch actually pass all three derived from the run's real `repository_filter` argument.
**Reasoning:** Without this fix, AC-4.8's repository-filter comparison would always compare the current run's filter against a checkpoint that always says "no filter," making every run with an actual `--repos`/`--exclude-*` restriction either falsely refused (if resumed with the same restriction, since `None != restriction`) or falsely allowed to proceed with a genuinely different filter than originally used (since a `None`-vs-`None` mismatch on the *exclude flags alone* was the only thing ever checked). This is a real, silent gap left by Story 10/11, not something Story 13 introduces — fixing it here is a precondition for AC-4.8 to mean anything for repository filters at all.
**Impact:** No existing test asserted `repository_filter` was ever passed to `CheckpointStore.create()` from `run.py` (Story 10/11's tests only checked `CheckpointStore` directly, with explicit values). New coverage: `TestResumeSafetyGuards::test_repository_filter_mismatch_refuses_resume_ac_4_8` and `test_matching_selection_and_filter_proceeds_to_resume` in `test_run.py`.

### DEV-13: A fail-fast-blocked run now creates the org directory, where it previously created nothing
**Story:** Story 13
**Planned:** FR-9's per-org claim needs a directory to hold its lock file (`<org_dir>/.run.lock`), acquired before preflight runs so two racing processes can't both proceed past the claim check.
**Actual:** `OrgClaim.acquire()` calls `org_dir.mkdir(parents=True, exist_ok=True)` unconditionally as part of acquiring the claim — meaning `<snapshot_root>/<org>/` now exists after *any* run attempt against that org, including one immediately refused by `--fail-fast` before a single network call. Story 10's `test_fail_fast_stops_before_creating_a_snapshot_dir_ac_6_4` originally asserted the org directory itself never got created in this case; updated it to assert instead that no *timestamped snapshot* directory was created inside it, which is what that test was actually protecting against.
**Reasoning:** The claim has to live somewhere on disk to be checked by a second concurrent process, and it has to be acquired before preflight (not after) for EC-13's "the second run is refused" to hold even when both processes reach the check at nearly the same instant — there's no way to satisfy both "claim first" and "touch nothing on disk on early refusal" simultaneously once a real claim mechanism exists. Creating an otherwise-empty org directory is an acceptable, narrow footprint in exchange for meaningfully racing-safe concurrent-run protection.
**Impact:** Only the one test above needed updating; its rewritten assertion still verifies the property that mattered (a fail-fast abort produces no partial snapshot).
